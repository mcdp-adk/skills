# 汉化制作

调查资源、组织制作或生成补丁时读取。以 [工作区](workspace-and-collaboration.md) 中明确的来源、编辑成果和处理记录开展制作，再从采用的成果生成补丁并验证实际效果。具体引擎、语言和资源格式决定实现方式；拆包、解密、回填、编译或运行时载入都不是每个项目必经的步骤。

## 调查来源与处理方法

从用户指定原版和已有材料确认版本、运行条件及资源组织。围绕约定范围调查内容分布和载入、显示依赖，用资源目录、脚本引用或代表界面相互核对，避免只围绕已提取文件寻找内容。遇到具体问题时，依据当前文件、运行信息及所用工具，查证相关实现与适用资料。原版只读，调查中的运行同样遵循 [数据保护](patch-verification.md#运行与数据保护)。

选择方法时核对现有材料和工具的输入输出：开发工程中的本地化功能未必能用于发行文件，能够提取资源也未必能写回。根据实际需要选择处理方法，通过 [制作验证](#验证制作方法) 判断它能否用于后续工作。

按实际作品关注剧情对白、角色称呼、选项、界面，以及涉及玩法的状态、道具、活动或动态组合。回想、分支和不同关系阶段可能共用或改变文字；不能只提取对白就宣称覆盖全部语言内容，也不要求每部作品都具备这些类型。

| 发现的机制 | 需要查清的关系 |
| --- | --- |
| 原生语言表或翻译脚本 | 游戏使用哪些标识、语境和载入配置，现成格式能否直接维护译文 |
| 剧本、事件、数据库或插件中的文字 | 哪些部分表达语言，哪些控制执行；系统页面、脚本属性或字符串运算是否另有显示内容；同一字符串是否还承担文件名、键或条件判断 |
| 封装、压缩或编译资源 | 实际读取入口、可用的提取或转换方法，以及修改后怎样被游戏接受 |
| 动态生成、外部载入或运行时替换 | 原文与使用语境如何定位、变量怎样组合、译文何时生效，是否另有缓存或优先级 |
| 图片文字、字形图集或特殊显示 | 哪些属于实际文字渲染，哪些是默认范围外的图片翻译；必要字体适配是否涉及字形图集 |

将已调查的位置、发现的内容及相关依赖保存为来源记录；未提取、读取失败和用途未明的部分注明缺口，继续调查时补充。记录粒度应足以定位待办和核对覆盖，可以按文件、资源组或具体条目组织，不要求枚举与任务无关的全部资源。局部抽取另存结果，不能覆盖已有的完整来源记录。

项目入口指向来源记录和操作说明，摘要说明可行方案、代表内容及实际材料缺口。首次无需穷尽资源；制作过程中继续核对约定范围，遇到不同机制补查，不能以已抽取或已制作的数量作为范围完整的依据。

## 准备制作材料

优先利用当前材料可用、能满足目标的现成工具和原生格式，按 [材料关系](workspace-and-collaboration.md#翻译材料的必要关系) 保留原文定位、可维护译文与上下文入口。没有可用的原生本地化机制时，建立当前游戏所需的最小处理方法；可以采用文件转换、补充语言资源或适用的运行时方式，不预先建设跨引擎平台。

按调查结果准备制作资源，以及帮助理解原文的材料，能直接引用就无需另复制一份。来源调查可以先记录位置、用途和未知项，再随制作提取具体内容；完整资源提取不作为翻译前置任务。

不同资源使用适合它们的维护形式：文字保留原文、语境和可编辑译文；已纳入的图片保留原图、引用位置及编辑成果；字体适配保留字体来源、使用位置和必要配置，字形或图集由这些材料生成或按工具原生方式维护。多处使用同一成果时保留引用关系；不因资源同名就合并，也不为统一格式而逐个登记字形。

译文的语言修订回到维护源；生成、装载和适配逻辑从维护源取得内容。原生翻译文件即使采用脚本语法，也可以直接作为维护源。来源相同、显示相同和译法相同分别核实；显示文字兼作资源键时，保留依赖或进行必要适配，不能无差别替换。

格式处理保持变量身份、控制关系、转义和编码有效，是否重排、拆句或改变条目数量由实际机制决定。根据读取端核对编码、字节序和标记，不默认全部转换成 UTF-8。原文或版本变化后核对对应关系，不把某种行号或引擎标识当永久不变的依据。未知来源、定位冲突或无法载入应明确报出，停止依赖操作；有意保留、未译和失败不能混作成功。

## 必要材料与用户选择

先调查现有材料是否足够，再提出具体缺口。查实际字体、样式、预渲染字形或图集和回退来源，区分字体差异与字号、字重、描边等设置造成的效果；系统界面与剧情文字也可能使用不同入口。发现两种视觉风格，并不直接要求用户提供两份字体。

需要选择时说明用途、推荐方案、来源要求和可见影响。例如正文与标题可以使用不同字体保留差异，也可能用同一字体配合样式；能否成立取决于实际加载与版面。使用一份字体的便利不能自动抵消风格变化，最终仍需验证。已有资源可用时直接沿用；确实需要用户提供或决定时再询问。

普通制作选择由 Agent 处理，明显影响作品风格或用户目标的取舍带依据交由用户决定。字体需适合简体中文呈现，并满足加工、随补丁分发的实际许可条件。系统字体回退可能掩盖未交付依赖，记录真正使用的资源；子集字体还需考虑约定支持的玩家输入，不能只覆盖固定译文。验证方法见 [中文显示](patch-verification.md#中文显示)。

材料缺失时先推进不依赖它的工作。资源状态、来源与已确定选择写回实际材料，不为每种潜在引擎预设一份文件清单。

## 验证制作方法

从已识别的不同处理或显示路径中选择少量代表内容，使用准备好的编辑文件完成制作和相应检查；语言内容按 [翻译与校对](translation-and-review.md) 处理。制作步骤从明确的维护源取得成果，让真实游戏使用它们，并生成能应用到测试原版的候选补丁。

记录足以重复执行的输入、步骤、输出和适用条件。可以是引擎操作、小型工具或可重复手工步骤；是否自动化由实际工作量决定。修改维护源后重新生成，按资源特点检查不同长度、字符、尺寸或控制信息等同类变化，按 [对应检查](patch-verification.md#按工作选择检查) 确认方法能用于后续内容。

诊断性改动只说明它实际验证的部分。叠加固定中文字、在工具里写死样本、只改测试副本或删掉原意以满足长度限制，都不能证明正式制作方法成立。扩大制作前，将试验中要沿用的成果、配置和操作纳入正式维护位置，确认来源可查、编辑位置明确、生成结果可重建；其余试验结果与构建输入分开。

## 成果采用与补丁生成

方法成立后，沿已验证路径扩大制作并补齐来源调查，新机制单独补验。翻译和引擎适配可以分工，接口以真实材料为准。发现问题先修对应维护源，再更新受影响结果，避免工程问题留到全量完成后才暴露。

从符合要求的成果中确定采用版本，记录实际维护位置和适用来源。采用决定可以与编辑成果一同维护；候选较多时用简单清单指向采用项，已有格式足够就直接沿用。生成成功、检查通过、决定采用和实机验证分别记录实际结果；采用不表示尚未执行的检查已经通过。未通过的候选继续修正或替换，对应任务仍保留；范围与质量取舍按正文的用户决定边界处理。

生成补丁时核对来源、采用的成果及该次输出所需的检查。来源不符、成果缺失或必要的译文校对或资源检查未完成时停止生成正式候选补丁；用于诊断的临时输出明确标识用途并另存。记录候选补丁采用了哪些成果，后续修改据此判断需更新和复验的部分。普通说明文档的追加不应自动改变采用版本，实际成果变化则须重新检查受影响内容。

补丁形态由实际安装与载入机制决定，可以是文件替换、语言资源、差分或必要的运行组件。核对封包覆盖优先级、已有补丁和必要配置，不能仅以包已生成判定游戏会采用它。仅包含约定的补丁内容及必要依赖，排除完整原版、个人数据、临时试验和无关工作文件。应用与恢复步骤依据真实方案编写，最终通过 [成品验收](patch-verification.md#成品验收) 后放入交付目录。
