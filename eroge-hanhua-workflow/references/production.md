# 汉化制作

调查制作方法、解决材料缺口或生成补丁时读取。通用链路是：定位来源与语境，维护译文和适配，使译文在游戏中生效，生成可重复应用的补丁，再验证实际结果。具体引擎、语言和资源格式决定实现方式；拆包、解密、回填、编译或运行时载入都不是每个项目必经的步骤。

## 初查与方案

从用户指定原版和已有材料确认版本、运行条件、资源组织与语言来源。先读入口、清单和代表文件，查明文字来源及其载入、显示方式，再按实际发现扩大调查。遇到具体问题时，依据当前文件、运行信息及所用工具，查证相关实现与适用资料。原版只读，调查中的运行同样遵循 [数据保护](verification.md#运行与数据保护)。

选择方法时核对现有材料和工具的输入输出：开发工程中的本地化功能未必能用于发行文件，能够提取原文也未必能写回。根据实际需要选择处理方法，通过第二阶段的代表链路验证它能否用于后续制作。

按实际作品关注剧情对白、角色称呼、选项、界面，以及涉及玩法的状态、道具、活动或动态组合。回想、分支和不同关系阶段可能共用或改变文字；不能只提取对白就宣称覆盖全部语言内容，也不要求每部作品都具备这些类型。

| 发现的机制 | 需要查清的关系 |
| --- | --- |
| 原生语言表或翻译脚本 | 游戏使用哪些标识、语境和载入配置，现成格式能否直接维护译文 |
| 剧本、事件、数据库或插件中的文字 | 哪些部分表达语言，哪些控制执行；系统页面、脚本属性或字符串运算是否另有显示内容；同一字符串是否还承担文件名、键或条件判断 |
| 封装、压缩或编译资源 | 实际读取入口、可用的提取或转换方法，以及修改后怎样被游戏接受 |
| 动态生成、外部载入或运行时替换 | 原文与使用语境如何定位、变量怎样组合、译文何时生效，是否另有缓存或优先级 |
| 图片文字、字形图集或特殊显示 | 哪些属于实际文字渲染，哪些是默认范围外的图片翻译；必要字体适配是否涉及字形图集 |

初查输出写入现有项目入口和操作说明：已确认的来源与版本、可行方案、代表内容、材料缺口和未证实的环节。首次无需穷尽全部资源；第二阶段用实际链路验证方案，制作中遇到不同机制再补查。

## 翻译材料与实际接口

优先利用当前材料可用、能满足目标的现成工具和原生格式，按 [材料关系](workspace.md#翻译材料的必要关系) 保留原文定位、可维护译文与判义入口。没有可用的原生本地化机制时，建立当前游戏所需的最小处理方法；可以采用文件转换、补充语言资源或适用的运行时方式，不预先建设跨引擎平台。

只读取或提取纳入内容及判义、制作实际需要的资源。图片可以帮助定位界面或人物动作，字体用于文字呈现；能直接引用就无需另复制一份。现成工具顺带导出的材料可以保留，完整资源整理不作为翻译前置任务。

译文的语言修订回到维护源；生成、装载和适配逻辑从维护源取得内容。原生翻译文件即使采用脚本语法，也可以直接作为维护源。来源相同、显示相同和译法相同分别核实；显示文字兼作资源键时，保留依赖或进行必要适配，不能无差别替换。

格式处理保持变量身份、控制关系、转义和编码有效，是否重排、拆句或改变条目数量由实际机制决定。根据读取端核对编码、字节序和标记，不默认全部转换成 UTF-8。原文或版本变化后核对对应关系，不把某种行号或引擎标识当永久不变的依据。未知来源、定位冲突或无法载入应明确报出，停止依赖操作；有意保留、未译和失败不能混作成功。

## 必要材料与用户选择

先调查现有材料是否足够，再提出具体缺口。查实际字体、样式、预渲染字形或图集和回退来源，区分字体差异与字号、字重、描边等设置造成的效果；系统界面与剧情文字也可能使用不同入口。发现两种视觉风格，并不直接要求用户提供两份字体。

需要选择时说明用途、推荐方案、来源要求和可见影响。例如正文与标题可以使用不同字体保留差异，也可能用同一字体配合样式；能否成立取决于实际加载与版面。使用一份字体的便利不能自动抵消风格变化，最终仍需验证。已有资源可用时直接沿用；确实需要用户提供或决定时再询问。

普通制作选择由 Agent 处理，明显影响作品风格或用户目标的取舍带依据交用户决定。字体需适合简体中文呈现，并满足加工、随补丁分发的实际许可条件。系统字体回退可能掩盖未交付依赖，记录真正使用的资源；子集字体还需考虑约定支持的玩家输入，不能只覆盖固定译文。验证方法见 [中文显示](verification.md#中文显示)。

材料缺失时先推进不依赖它的工作。资源状态、来源与已确定选择写回实际材料，不为每种潜在引擎预设一份文件清单。

## 代表链路与重建

从已识别的不同处理或显示路径中选择少量代表内容，按 [材料关系](workspace.md#翻译材料的必要关系) 准备原文、译文及判义入口，使翻译与审校者能定位、理解和修改内容，再按 [翻译与审校](translation.md) 处理样本。制作步骤从这些维护材料取得译文，让真实游戏使用它们，并生成能应用到测试原版的候选补丁。

记录足以重复执行的输入、步骤、输出和适用条件。可以是引擎操作、小型工具或可重复手工步骤；是否自动化由实际工作量决定。修改维护源后重新生成，检查不同长度、字符或相关控制信息等同类变化，按 [链路检查](verification.md#按阶段选择检查) 确认方法能用于后续内容。

诊断性改动只说明它实际验证的部分。叠加固定中文字、在工具里写死样本、只改测试副本或删掉原意以满足长度限制，都不能证明正式译文路径成立。临时方案若要用于后续制作，需纳入维护来源和实际加载链路，并检验其适用范围。

## 扩展与补丁生成

方法成立后，持续盘点全部纳入来源及其去向，沿已验证路径扩大制作；新机制单独补验。翻译和引擎适配可以分工，接口以真实材料为准。发现问题先修对应维护源，再更新受影响结果，避免工程问题留到全量完成后才暴露。

补丁形态由实际安装与载入机制决定，可以是文件替换、语言资源、差分或必要的运行组件。核对封包覆盖优先级、已有补丁和必要配置，不能仅以包已生成判定游戏会采用它。仅包含约定的补丁内容及必要依赖，排除完整原版、个人数据、临时试验和无关工作文件。应用与恢复步骤依据真实方案编写，最终通过 [成品验收](verification.md#成品验收) 后放入交付目录。
