# 验证与交付

本参考负责检查方法、游戏运行与最终交付验收；翻译材料和构建职责见[工作材料与流程衔接](materials.md)。启动游戏前查[测试环境与用户数据保护](#测试环境与用户数据保护)，安排检查时查[选择检查](#选择检查)，区分证据范围时查[验证概念](#验证概念)，处理显示问题时查[字体与布局](#字体与布局)，进入特定场景时查[到达测试场景](#到达测试场景)，交付或复用旧证据时查[确认交付对象](#确认交付对象)。

## 验证概念

先说明要检查的对象和结果，再描述采用的方法。下列维度可以组合，并非需要分别建设的测试系统：

| 维度 | 含义与边界 |
| --- | --- |
| 检查目的 | 语言审校判断含义与中文表达；程序检查核对格式、引用和处理逻辑；真实运行观察显示与相关行为。程序结构正确不能代替语言或画面正确 |
| 是否执行被测逻辑 | 静态检查读取文件及其关系；动态检查执行被测游戏、引擎或组件。解析脚本文件属于静态检查，运行其中的插值逻辑属于动态检查 |
| 经过的流程 | 局部检查只覆盖某个环节；端到端验证按声明的起止点经过真实流程，例如从菜单选择进入剧情并看到结果。一次端到端取样不等于走完全部剧情 |
| 操作手段 | 脚本、Computer Use 等用于执行检查。脚本既能分析文件，也能操控游戏；鼠标点击与截图本身不决定验证是否充分 |

“动态文字”指插值、拼接或按条件生成的文字；它描述内容的生成方式，与“动态检查”区分。可以静态检查它的模板，也可以执行代表性输入。用独立解释器求值能证明该处局部逻辑的结果，不能自动证明游戏实际加载和呈现相同。

覆盖范围同样需要指明对象：

| 覆盖对象 | 记录什么 |
| --- | --- |
| 文本来源与制作 | 哪些纳入内容已找到、登记、翻译和回填，哪些尚未处理 |
| 语言审校 | 哪些内容已完成双语对照和中文连读；要求覆盖全部纳入内容 |
| 运行取样 | 实际执行并观察的流程、状态和输入，按改动与风险选择 |

一次菜单取样可以覆盖菜单的显示与操作，同时只覆盖少量文本。文件清单完整、语言审校完整和运行取样通过分别说明，避免用一个“全量通过”混合这些结论。

需要核对静态与动态的术语时，可查 [ISTQB CTFL 4.0.1，第 3.1.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。引擎环境名称不替代上述判断，例如 [Unity 的 Edit Mode 与 Play Mode](https://docs.unity3d.com/Packages/com.unity.test-framework@2.0/manual/edit-mode-vs-play-mode-tests.html)。

## 选择检查

本参考中的**候选补丁**是准备应用和验收的一版交付内容；**被测对象**是实际接受检查的文件、组件或应用补丁后的测试副本。候选、测试副本与生成它们的工具相互关联，但各自的检查结论不能直接替换。

按当前对象确定范围，再选择适用检查。优先使用目标格式已有的工具，核实实际覆盖的内容，再补足缺项。

| 当前对象 | 检查如何取舍 |
| --- | --- |
| 代表样本 | 覆盖所选提取、回填与显示路径，核对样本结构、中文显示和相关操作；尚未制作的内容保留为后续事项 |
| 制作批次 | 核对本批来源覆盖、格式、引用及语言，按新的字体、布局或逻辑改动及时运行取样；发现新路径先验证它 |
| 完整候选 | 核对全部纳入内容的处理与审校状态、完整译文字形和实际包的应用结果，按风险观察代表流程 |
| 局部修订 | 沿实际依赖确定回归范围；共用词、字体或拼接规则的改动可能影响多个场景，纯局部改动无需重验无关路径 |

例如，样本之外尚未翻译的日文在中文字体下缺字，应记录其过渡状态；它不自动否定已正确显示的中文样本。最终纳入范围的未译或缺字则必须处理。

### 样本方法的适用范围

样本用来判断处理路径能否服务于后续制作。既检查样本的实际表现，也检查结果如何产生：

- 从原文和译文基准出发，按记录的步骤将结果应用到干净测试副本；仅手改某个测试副本得到的画面，还需回到维护来源完成重建。
- 根据该路径的实际限制选择少量同类变化，例如不同长度、字符或占位符组合。确认方法仍能保持含义、结构和相关行为，不能只凭一条固定文本的成功推及同类内容。
- 保留重建所需的输入、操作与适用条件。可重复的手工步骤也可以成立；是否编写脚本取决于工作量和重复操作的成本。

为定位问题所作的临时修改，记录其用途和局限；只有纳入正式处理路径并验证适用范围的部分，才作为后续制作依据。额外叠字或固定输出若未读取待交付的译文，只能证明该显示试验；删掉原意来凑字节长度也不能证明回填方法成立。采用文件替换、运行时拦截或其他方式时，都应验证实际的译文载入与显示路径。样本只验证已识别的主要路径，其他独立路径在遇到时补验，不据此扩建通用工具框架。

### 按问题选择证据

| 检查对象 | 应取得的证据 |
| --- | --- |
| 文本来源与回填 | 将原文来源与处理结果逐项对应，查缺失、重复、错位及未判定项。汉字短标签、代码内显示值和动态来源也须有去向，残留扫描用于发现可疑位置 |
| 格式与控制结构 | 按目标格式解析、编译或 lint，检查编码、转义、占位符身份、类型和数量，以及标签作用范围；允许的重排与错误变更要分开判断 |
| 资源引用与内部标识 | 沿调用关系核对实际键和文件，包含动态生成的引用。对照原版区分已有缺失与汉化新增缺失 |
| 动态表达 | 检查各类完整表达和条件分支，执行代表性输入及相关边界，观察生成结果；语言组合方法见[动态组合](translation.md#动态组合) |
| 术语与审校修改 | 回查相关称谓、共用词和组合片段，确认修正已进入译文基准及受影响资源 |
| 候选补丁 | 核对包内译文、字体和必要配置，确认其来自当前工作材料，再检查应用后的测试副本 |

结合程序检查，观察真实游戏中改动涉及的显示和流程。例如改姓名输入，观察输入后的完整句子；改选项，核对文字与触发行为；改字体，观察对应显示位置。记录游戏版本、补丁对象、所处状态与观察结果。取样无需逐文件游玩或穷尽剧情分支。

### 核实检查本身

判断检查是否有效，要看它读取了什么、运行了什么以及怎样判定。文件中的字节命中不能证明目标对象的结构或显示正确；无缺字日志也不能证明尚未出现的对白可读。对承担关键通过判定的自写或可疑检查，用有效样本和针对性反例核实判定，再作必要修正。检查器返回成功、游戏启动成功和目标画面正确分别提供不同证据。

工具运行结束后，读取检查结果，区分通过项、失败项和未覆盖部分。[Ren'Py 开发工具文档](https://www.renpy.org/doc/html/developer_tools.html)说明 lint 不能替代充分测试；适用命令和检查缺口仍由目标引擎决定。[IGDA LQA 实践](https://igda.org/news-archive/how-to-get-the-most-from-lqa-what-it-is-and-best-practices/)可用于安排游戏内语言、界面和上下文观察，并在修复后回归。

## 字体与布局

先沿实际显示路径查字体来源：全局默认、局部样式、脚本显式指定、输入控件及回退字体可能各不相同。按各用途的中文需求选择字体，决定是否加工、子集化及怎样接入；所需字体数量由游戏决定。

覆盖检查包括译文中的汉字、标点、符号，以及约定支持的玩家中文输入。只用现有译文取字生成子集，可能使玩家新输入的姓名缺字。为输入范围提供足够字形或可用回退，再核对实际加载的文件与字形来源。

依次区分以下问题，采用目标字体格式或引擎适用的方法：

| 问题 | 证据与限制 |
| --- | --- |
| 字体有无所需字形 | 检查字符到字形的实际映射；使用图集的格式还需核对相关图集，或采用等价引擎接口。原始码点字节命中不足以证明可用 |
| 游戏是否使用该字体 | 沿实际资源引用、样式与回退规则确认。字体文件已放入目录不等于目标控件已经加载 |
| 画面是否正确 | 在目标显示位置观察缺字、意外回退、断行、字宽、遮挡及按钮可读性。一个字符或页面成功不能推及全部位置 |

字形齐全但文字被裁切时，继续检查布局与字体度量等实际原因；单纯通过缺字检查不足以完成显示验证。

需要加工或随补丁分发字体时，核对来源与许可条件，保留所需许可说明。[Godot 国际化文档](https://docs.godotengine.org/en/4.5/tutorials/i18n/internationalizing_games.html)介绍字体覆盖及回退问题；[Ren'Py Text](https://www.renpy.org/doc/html/text.html) 展示字体、插值、样式与排版的处理环节。参考时按实际引擎确认接入机制。

## 测试环境与用户数据保护

### 启动前的保护措施

测试的目的是真实验证补丁，同时尽量不影响用户环境和已有进度。使用独立游戏副本，查清可能覆盖用户存档、改变重要设置或干扰验证的写入；复制游戏目录不保证运行数据独立。优先使用引擎已有的数据目录配置、独立档位或其他能达到保护目的的简单办法，必要时再检查环境变量、用户数据目录或注册表。

根据实际风险决定措施。普通日志或缓存位于工作目录外，不单独构成暂停理由；若它们共享用户状态、影响结果或涉及受保护位置，仍需处理。可重定向的数据优先放入测试位置；需要接触实际用户数据时按明确授权操作，使用备份测试副本，必要的恢复步骤也应有依据。修改实际游玩存档另需明确授权。

明确禁止访问的位置始终排除。仍无法排除覆盖用户进度或重要设置的风险时，暂停该次运行，说明具体缺口并选择替代办法，继续独立工作。无需为证明所有系统写入都在某个目录内而建设隔离框架；任何阶段启动游戏都遵循本节，已有有效保护安排可沿用。

[Microsoft 应用数据文档](https://learn.microsoft.com/en-us/windows/apps/develop/data/store-and-retrieve-app-data)介绍本地、漫游和临时数据，是游戏目录之外可能存在状态的例子；目标游戏的具体位置需另查。

### 持久化状态与旧档

**持久化状态**是跨次运行保留的存档、设置等数据。它可能保存显示文字、资源引用或派生缓存，读取时覆盖包内初值。独立测试数据描述数据的用途与边界，不代表已验证真实旧档兼容。出现异常时追查当前值从包、初始化、存档还是缓存而来：

| 现象 | 优先核对 |
| --- | --- |
| 新游戏仍显示旧译文 | 实际载入的包、语言设置和初始化来源 |
| 新游戏正确，旧档显示不同 | 存档保存了哪些值，以及读档怎样覆盖当前值 |
| 文字已修正，图片仍缺失 | 可见文字与资源引用各自的来源和对应关系 |

需要旧档兼容时，先明确项目范围及使用测试数据的授权。ID 可能重复，下标可能随版本变化，依据实际结构确认匹配关系。若要迁移，使用同一译文基准更新确认的显示内容或必要引用，并检查进度、数量等其他状态保持不变；备份与回滚随具体写入安排。是否制作迁移工具由查明的兼容需求决定，用户存档的访问和写入仍遵循约定权限。

## 到达测试场景

为待验证的显示或行为选择可用入口，优先利用现成测试存档、章节选择、回想或开发入口。正常游玩到达成本明显较高且需要检查该场景时，可构造独立测试存档或状态；先查明必要字段、依赖和状态约束，只修改达到目标所需的内容。是否编写生成工具由实际复用价值决定。

由游戏实际载入该状态，观察目标画面及相关操作，记录状态来源、必要改动、入口与观察范围。载入失败时检查构造状态与资源的关系，不能直接归因于补丁。构造状态下显示正确只证明所测状态；自然游玩可达性、存读档行为和真实旧档兼容需各自的证据。

测试数据遵循上一节的保护与授权要求。没有获授权的真实旧档时，可以验证独立测试存档，但应明确真实旧档兼容尚未验证。

## 成品验收

第四阶段从指定版本的干净测试副本应用实际候选补丁，按以下维度确定检查范围。全面验收要求各适用维度都有依据，不等于穷尽所有玩法，也不等于仅观察一个菜单。第一阶段的初查不能替代第二阶段的真实链路验证，第二阶段样本也不能替代本节的成品验收。

| 维度 | 验收内容 |
| --- | --- |
| 内容完整性 | 核对纳入来源、译文、全量双语审校和中文连读状态，以及实际回填结果；扫描发现的残留逐项辨别，范围外保留内容明确说明 |
| 字体与呈现 | 检查完整译文及约定输入范围的字符支持；在游戏中覆盖各类显示方式，观察不同界面、长短文本、动态组合的缺字、换行、遮挡和可读性，方法见[字体与布局](#字体与布局) |
| 操作与流程 | 按实际改动检查相关导航、选项与分支、输入、剧情推进及存读档；共用脚本、字体或运行逻辑变化应扩大到其影响范围，不只测修改发生的单一页面 |
| 语境与整体表达 | 结合实际场景检查人物口吻、指代、选项区别与跨批次一致性；按[双语审校](translation.md#双语审校)纠错和润色，修改后回对原文 |
| 应用与交付 | 验证说明中的应用步骤和必要文件，确认最终包与已测版本一致，说明版本要求、许可、兼容范围和必要的恢复方式 |

按显示路径与改动风险选择场景；需要后期内容时查[到达测试场景](#到达测试场景)，无需仅为到达画面从头手动游玩，但自然流程和存读档行为需要相应证据。首版从新游戏测试不代表永久排除旧档；旧档反馈按授权及[持久化状态与旧档](#持久化状态与旧档)调查。

每项记录对象、方法、实际结果与未覆盖部分。区分原版缺陷、汉化问题和测试状态影响；有原版对照时沿相同条件核对，没有对照时标为待查。发现问题先修维护来源，再生成并复查受影响结果。无法达到约定要求时，带具体缺口和可行取舍请用户决定，不把未执行的验收写成通过。

## 确认交付对象

### 对象一致性

对照约定，核实独立测试副本应用的是实际候选补丁，审校和修复已经进入该补丁。哈希或包清单可证明对象和内容是否一致，运行与语言质量由对应检查证明。

修复后复查受影响部分。若只改变打包元数据，先辨明内容差异，再决定哪些结果仍适用；新补丁沿用旧运行记录时，应能说明对应内容和运行条件未受影响。

### 复用证据与工具故障

证据有效性与测试工具当前可用性分别判断。工具修订或一次启动前失败，不自动推翻同一候选已有的运行、显示及数据保护证据；旧结果也不能证明新工具已验证。出现候选变化、相关运行条件变化、相反证据或检查曾有误判时，重新判断受影响结论，补足实际缺口。未来仍需运行的检查必须具备可用且满足数据边界的手段，再次启动前确认已有保护措施仍适用。

工具故障先定位它阻塞的必要操作，选择修复、替换或其他足够的方法；未受影响的制作继续。保留能够追溯候选与结果的必要记录即可，工具版本本身是否需要核验取决于它是否影响具体结论。

### 结果与结论

记录实际发生的结果：是否启动、目标流程是否执行、如何结束、用户数据是否受到预期保护，必要时是否已还原临时改动。正常定时停止与提前失败分别判断；恢复成功只证明恢复结果，不能把没有启动的尝试记作运行通过。

发现异常时，根据对应原版、译文来源与状态数据区分原因。没有原版对照时，将疑似原版问题保留为待查；日志警告本身不能确定责任。检查记录写清对象、方法、结果和局限，尚未执行的检查列为未验证。将这些实际结果带入交付说明，按正文约定交付补丁及必要维护材料。
