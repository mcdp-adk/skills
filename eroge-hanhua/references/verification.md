# 补丁验证

本参考用于日文 R18 游戏汉化中的程序检查、字体适配和运行观察。启动游戏前查[隔离与运行状态](#隔离与运行状态)，安排检查时查[验证概念](#验证概念)和[选择检查](#选择检查)，处理显示问题时查[字体与布局](#字体与布局)，交付前查[确认交付对象](#确认交付对象)。

## 验证概念

以下概念回答不同问题：静态与动态区分是否执行被测逻辑，端到端描述经过多大范围的真实流程，语言审校判断译文含义与表达。

| 概念 | 判断依据 | 证据范围 |
| --- | --- | --- |
| 静态验证 | 检查文件及其关系，未执行被测游戏或被测逻辑 | 解析脚本、比较资源键和占位符、核对包清单；结果限于所检查的结构与关系 |
| 动态验证 | 执行被测游戏、引擎或组件，观察实际结果 | 执行插值表达式、读档或运行游戏；结果限于执行过的环境、输入和状态 |
| 端到端验证 | 从玩家入口经过真实流程，直到可观察的结果 | 如从菜单进入剧情、选择选项并看到结果；运行局部表达式只覆盖其中一部分 |
| 语言审校 | 对照原文和上下文，判断译文意义及中文表达 | 可在文件中或游戏内完成，程序结构正确与语言正确需分别检查 |

脚本和 Computer Use 是操作手段。脚本可以静态检查文件，也可以动态执行逻辑或操控真实流程；用隔离解释器求值提取出的数组表达式，属于局部动态验证。Computer Use 提供真实界面的操作与观察，记录中仍要说明实际走过的流程。

**文本覆盖**描述纳入范围的语言内容是否被发现、登记和处理；**运行验证覆盖**描述执行并观察过的流程、状态和输入组合。全量翻译与审校按文本范围完成，运行观察按实际改动和风险取样，两种范围分别说明。

概念依据可查 [ISTQB CTFL 4.0.1，第 3.1.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)中的静态、动态测试区分。[Unity 的 Edit Mode 与 Play Mode](https://docs.unity3d.com/Packages/com.unity.test-framework@2.0/manual/edit-mode-vs-play-mode-tests.html)划分的是运行环境，不能据其名称直接判断静态或动态。

## 选择检查

让检查对应可能出错的位置。优先使用目标格式已有的工具，核实它们实际覆盖的内容，再补足缺项。

| 检查对象 | 应取得的证据 |
| --- | --- |
| 文本来源与回填 | 将原文来源与处理结果逐项对应，查缺失、重复、错位及未判定项。汉字短标签、代码内显示值和动态来源也须有去向，残留扫描用于发现可疑位置 |
| 格式与控制结构 | 按目标格式解析、编译或 lint，检查编码、转义、占位符身份、类型和数量，以及标签作用范围；允许的重排与错误变更要分开判断 |
| 资源引用与内部标识 | 沿调用关系核对实际键和文件，包含动态生成的引用。对照原版区分已有缺失与汉化新增缺失 |
| 动态表达 | 检查各类完整表达和条件分支，执行代表性输入及相关边界，观察生成结果；语言组合方法见[动态组合](translation.md#动态组合) |
| 术语与审校修改 | 回查相关称谓、共用词和组合片段，确认修正已进入译文基准及受影响资源 |
| 候选补丁 | 核对包内译文、字体和必要配置，确认其来自当前工作材料，再检查应用后的测试副本 |

结合程序检查，使用适量 Computer Use 观察改动涉及的显示和流程。例如改姓名输入，观察输入后的完整句子；改选项，核对文字与触发行为；改字体，观察对应显示位置。记录游戏版本、补丁对象、所处状态与观察结果，使结论能对应实际证据。取样无需逐文件游玩或穷尽剧情分支。

工具运行结束后，读取检查结果，区分通过项、失败项和未覆盖部分。[Ren'Py 开发工具文档](https://www.renpy.org/doc/html/developer_tools.html)说明 lint 不能替代充分测试；适用命令和检查缺口仍由目标引擎决定。[IGDA LQA 实践](https://igda.org/news-archive/how-to-get-the-most-from-lqa-what-it-is-and-best-practices/)可用于安排游戏内语言、界面和上下文观察，并在修复后回归。

## 字体与布局

先沿实际显示路径查字体来源：全局默认、局部样式、脚本显式指定、输入控件及回退字体可能各不相同。按各用途的中文需求选择字体，决定是否加工、子集化及怎样接入；所需字体数量由游戏决定。

覆盖检查包括译文中的汉字、标点、符号，以及约定支持的玩家中文输入。只用现有译文取字生成子集，可能使玩家新输入的姓名缺字。为输入范围提供足够字形或可用回退，再核对实际加载的文件与字形来源。

分别保留三类证据：字体文件包含所需字形，显示规则指向预期字体，以及游戏实际呈现正确。运行时观察缺字、意外回退、断行、字宽、遮挡和按钮可读性。单个字符显示正确只证明该处状态，不能推及整个字符范围。

需要加工或随补丁分发字体时，核对来源与许可条件，保留所需许可说明。[Godot 国际化文档](https://docs.godotengine.org/en/4.5/tutorials/i18n/internationalizing_games.html)介绍字体覆盖及回退问题；[Ren'Py Text](https://www.renpy.org/doc/html/text.html)展示字体、插值、样式与排版的处理环节。参考时按实际引擎确认接入机制。

## 隔离与运行状态

测试副本的游戏文件与运行数据都要隔离。根据目标引擎和平台查明写入位置，必要时检查配置、环境变量、用户数据目录或注册表。复制游戏目录后仍可能写入共享位置；确认测试的存档、设置、日志和缓存落在约定范围内，再启动。无法确认时暂停启动，说明尚缺的条件，继续不依赖运行的工作。

[Microsoft 应用数据文档](https://learn.microsoft.com/en-us/windows/apps/develop/data/store-and-retrieve-app-data)介绍本地、漫游和临时数据，是游戏目录之外可能存在状态的例子；目标游戏的具体位置需另查。

**持久化状态**是跨次运行保留的存档、设置等数据。它可能保存显示文字、资源引用或派生缓存，读取时覆盖包内初值。出现异常，追查当前值从包、初始化、存档还是缓存而来：

| 现象 | 优先核对 |
| --- | --- |
| 新游戏仍显示旧译文 | 实际载入的包、语言设置和初始化来源 |
| 新游戏正确，旧档显示不同 | 存档保存了哪些值，以及读档怎样覆盖当前值 |
| 文字已修正，图片仍缺失 | 可见文字与资源引用各自的来源和对应关系 |

需要旧档兼容时，先明确项目范围及使用测试数据的授权。ID 可能重复，下标可能随版本变化，依据实际结构确认匹配关系。若要迁移，使用同一译文基准更新确认的显示内容或必要引用，并检查进度、数量等其他状态保持不变；备份与回滚随具体写入安排。是否制作迁移工具由查明的兼容需求决定，用户存档的访问和写入仍遵循约定权限。

## 确认交付对象

对照约定，核实独立测试副本应用的是实际候选补丁，审校和修复已经进入该补丁。哈希或包清单可证明对象和内容是否一致，运行与语言质量由对应检查证明。

修复后复查受影响部分。若只改变打包元数据，先辨明内容差异，再决定哪些结果仍适用；新补丁沿用旧运行记录时，应能说明对应内容和运行条件未受影响。

检查记录写清对象、方法、结果和局限。区分原版已有缺陷、汉化引入的问题及状态影响；尚未执行的检查列为未验证。缺字截图、残留扫描或某次启动成功各自只支持有限结论。将这些实际结果带入交付说明，按正文约定交付补丁及必要维护材料。
