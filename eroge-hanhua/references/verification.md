# 验证与交付

按改动和风险选检查方法。下面解释各类证据的用途，并展开字体、隔离和持久化状态的处理；具体引擎、工具与检查次数由项目决定。

## 验证概念

| 概念 | 判断依据 | 示例与限制 |
| --- | --- | --- |
| 静态验证 | 没有执行被测游戏或被测逻辑，只检查文件及其关系 | 解析脚本、比较资源键、核对占位符和包清单；不能证明实际加载与渲染 |
| 动态验证 | 执行被测游戏、引擎或组件并观察结果 | 运行插值表达式、读档或操作游戏；结论限于实际执行的环境和状态 |
| 端到端验证 | 从玩家入口经过真实流程到可观察结果，描述的是测试范围 | 从菜单进入剧情、作出选择并观察结果；脚本自动化也可以执行这种检查 |
| 语言审校 | 对照原文和上下文判断译文意义与表达 | 可发生在文件审校或游戏观察中；解析成功不能证明语言正确 |

脚本与 Computer Use 是执行方式，不能分别等同于静态与动态。例如脚本通过隔离的解释器执行提取出的数组表达式，已经执行被测逻辑；它只能证明局部输出，不能证明真实引擎会按相同状态读取并渲染。

静态与动态区分可参考 [ISTQB CTFL 4.0.1，第 3.1.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。[Unity 的 Edit Mode 与 Play Mode](https://docs.unity3d.com/Packages/com.unity.test-framework@2.0/manual/edit-mode-vs-play-mode-tests.html)区分运行环境，两者也不是静态与动态的同义词。

## 选择检查对象

| 改动或风险 | 实际检查 |
| --- | --- |
| 提取、回填或来源变化 | 对照原文来源与处理记录，检查缺失、重复、错位和未判定项。含汉字的短标签、代码内显示值和动态来源都要能被记录；残留扫描只帮助找候选 |
| 格式或控制结构受影响 | 使用适用的解析、编译或 lint，检查编码、转义、占位符类型与数量、标签作用范围。按格式允许的变化判断，不能一律要求文本结构零差异 |
| 文本兼作资源键或标识 | 沿调用关系检查实际文件和键，包括动态生成的引用。比较原版已有缺失与新增缺失，避免把所有日文路径都改成中文 |
| 姓名、数值或片段拼接 | 检查完整表达与条件关系，运行代表性输入和边界组合，观察最终显示。按语法分支核对各类输出，不要求穷举所有玩家输入 |
| 术语或审校结果更新 | 回查共用词、称谓、短标签与组合片段，确认修改进入译文基准及受影响的交付资源 |
| 重新打包 | 核对包内文件与当前译文源、字体和必要配置，再用候选补丁建立测试对象。包清单与哈希可确认身份，不能证明语义和运行正确 |

尽早用少量代表性内容验证陌生处理方式，避免翻译完成后才发现无法正确回填。已有引擎工具合适时直接使用；[Ren'Py 开发工具](https://www.renpy.org/doc/html/developer_tools.html)明确说明 lint 不能替代充分测试。通用做法是核对工具实际检查了什么，不把某个引擎的命令固定为所有项目步骤。

界面观察关注实际改动：改输入就观察输入后的句子，改字体就观察对应显示，改选项就检查文字与触发行为的关系。运行记录应能说明检查了哪个状态、看到了什么。少量截图不能替代全量双语审校，也不要求逐文件游玩或穷尽剧情分支。

## 字体与布局

沿实际显示路径查字体：全局默认、局部样式、脚本显式字体、输入控件及回退字体都可能不同。先确认需要哪些用途，再选字体，避免把替换一个文件当作完成接入。

将译文字符、标点、符号及约定的玩家中文输入需求纳入覆盖检查。只按现有译文取字做子集，可能使新输入的姓名缺字；需有覆盖输入范围的字体或可用回退。核对实际被加载的文件和字形来源，再观察缺字、替代字体、断行、字宽、遮挡及按钮可读性。字体文件包含某字、CSS 映射正确、界面恰好显示出某字，分别提供不同证据。

需要加工或随包分发字体时，核对来源和许可条件，并随交付物保留所需说明。字体数量、是否子集化及样式映射均由项目需求决定。

[Godot 国际化文档](https://docs.godotengine.org/en/4.5/tutorials/i18n/internationalizing_games.html)说明默认字体覆盖与回退的限制；[Ren'Py 文本处理](https://www.renpy.org/doc/html/text.html)将字体、插值、样式和排版作为不同环节。这些来源用于理解检查对象，不证明目标项目已启用对应机制。

## 隔离与持久化状态

复制游戏目录不一定隔离了运行数据。根据引擎和平台调查实际写入位置，必要时检查配置、环境变量、用户数据目录或注册表。先让测试运行使用独立位置；无法确认时暂停启动，说明尚需解决的条件，继续不依赖运行的工作。测试过程中生成的存档和日志也留在约定边界内。

[Microsoft 应用数据文档](https://learn.microsoft.com/en-us/windows/apps/develop/data/store-and-retrieve-app-data)展示了本地、漫游与临时数据的区别，仅作为目录之外还可能有状态的例证；实际游戏的位置和生命周期仍要调查。

显示异常时，沿“包内初值 → 初始化 → 读档 → 派生显示”查当前取值来源：

- 新游戏也显示旧译文，先看实际包、语言设置和初始化来源。
- 新游戏正确、旧档不正确，查看存档是否保存标题、正文、资源引用或缓存，以及读档是否覆盖新值。
- 文字正确而图片缺失，分别检查资源引用和可见文字，修好其中一项不代表另一项通过。

若约定需要旧档兼容，先在获准使用的测试数据上确认对应关系。ID 可能重复，数组下标也可能随版本变化，匹配方法要有证据。需要同步时读取同一译文基准，只更新确认的显示内容或必要引用，并检查进度、数量等其他状态未被误改。备份和回滚随具体写入安排；不能把制作补丁视为允许改用户存档，也不为每个项目预建迁移程序。

## 交付结论

确认测试副本应用的是实际候选补丁，审校和修复已进入该补丁。变更后检查受影响部分；若只是打包元数据变化，辨明内容差异后决定复查范围，不机械重测无关内容。

结论写清版本、对象、方法和结果，并区分剩余问题与未验证部分。例如“该输入下姓名显示正确”只证明该状态；“交付包与测试包内容一致”只证明对象一致。原版缺陷、汉化错误和状态影响按证据分别说明，未执行的检查保留为未验证。

[IGDA 的 LQA 实践](https://igda.org/news-archive/how-to-get-the-most-from-lqa-what-it-is-and-best-practices/)强调在游戏内观察语言、界面和上下文，并在修复后回归。其行业经验可帮助选择检查内容，不要求所有个人项目采用固定测试矩阵。
